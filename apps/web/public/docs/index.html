ArchScript language reference.

ArchScript is a small DSL for describing software architecture as code. It models systems, components, domains, environments, relations, metadata and architecture rules, then generates diagrams, documentation and reports.

Language

What ArchScript describes

An ArchScript file describes a software system as structured architecture data. The same source can generate PlantUML diagrams, Markdown documentation, SVG, PNG and PDF architecture reports.

project SaaSPlatform

element frontend "Customer Portal" as portal
element service "Tenant API" as tenant_api
element database "Tenant Database" as tenant_db

relation portal -> tenant_api : REST
relation tenant_api -> tenant_db : PostgreSQL

Define the architecture name

Every ArchScript file starts with a project declaration. The project name is used as the diagram title and as the main heading in generated documentation and reports.

project SaaSPlatform

Model architecture building blocks

Elements represent the building blocks of a software system. They can be users, teams, frontends, backends, services, databases, queues, gateways, external APIs, storage systems, identity providers and more.

element actor "Customer" as customer
element frontend "Web App" as webapp
element service "Customer API" as api
element database "PostgreSQL" as db
element event_bus "Event Bus" as event_bus
element identity_provider "Keycloak" as idp

Separate display names from stable identifiers

Use `as` to assign a stable technical ID to an element. Relations should reference IDs, not display names. This keeps relationships stable even when you rename labels.

element service "Customer API" as customer_api

element database "Customer Database" as customer_db

relation customer_api -> customer_db : PostgreSQL

Add metadata to your architecture

Properties enrich elements and relations with architecture metadata such as technology, owner, monitoring and descriptions. This metadata is used in generated documentation and detailed diagrams.

element service "Billing Service" as billing {
  tech "Rust"
  owner "Platform Team"
  monitoring "Grafana"
  description "Handles subscription billing"
}

relation billing -> billing_db {
  protocol "PostgreSQL"
  description "Stores billing records"
}

Classify elements and relations

Tags classify architecture elements and relations. They are useful for filtering, documentation, rules and future visual views. Tags are written as arrays.

element service "Tenant API" as tenant_api {
  owner "Backend Team"
  monitoring "Grafana"
  tags [critical, production]
}

relation portal -> tenant_api {
  protocol "REST"
  tags [sync, public]
}

Describe dependencies and communication

Relations describe how elements communicate or depend on each other. They can use a short label or a full property block.

relation portal -> api : REST

relation api -> event_bus {
  label "publishes OrderCreated"
  protocol "Kafka"
  tags [async, event-driven]
}

Group elements by technical boundaries

Boundaries group elements into technical or logical areas such as Client, Backend, Infrastructure or Messaging.

boundary Client {
  element actor "Customer" as customer
  element frontend "Web App" as webapp
}

boundary Backend {
  element service "API" as api
  element database "PostgreSQL" as db
}

Model business capabilities and bounded contexts

Domains represent business capabilities or DDD bounded contexts. They are useful for microservice architectures, modular monoliths and product platforms.

domain Billing {
  element service "Billing Service" as billing
  element database "Billing Database" as billing_db
}

domain Identity {
  element service "Auth Service" as auth
  element database "Auth Database" as auth_db
}

Represent deployment stages

Environments model where architecture elements run. Common examples are Development, Staging and Production.

environment Production {
  element cdn "CDN" as cdn
  element frontend "Customer Portal" as portal
  element gateway "API Gateway" as gateway
  element service "Tenant API" as tenant_api
  element database "Tenant Database" as tenant_db
}

Architecture Rules

Built-in architecture review

ArchScript includes a rule engine that checks architecture constraints. Rule violations do not block diagram generation, but they appear in the Playground and in PDF reports.

no_frontend_to_database

Prevents frontend elements from directly accessing database-like elements.

critical_requires_owner

Requires every element tagged as critical to define an owner property.

production_requires_monitoring

Requires production elements to define monitoring metadata.

element service "Billing Service" as billing {
  tags [critical, production]
}

# Rule output:
# Critical element 'Billing Service' requires owner property
# Production element 'Billing Service' requires monitoring property

Exports

Generate architecture artifacts

ArchScript can export multiple artifacts from the same source model.

PlantUML

Use generated PlantUML in existing architecture documentation pipelines.

SVG / PNG

Export rendered diagrams for presentations, documentation and reports.

PDF Report

Generate a branded architecture report with diagram, documentation and review results.

Markdown

Produce text documentation that can be stored in repositories or wikis.

.archscript

Save and version your architecture source as a dedicated DSL file.

JSON Result

The compiler exposes structured output for future integrations and extensions.

A production SaaS architecture

This example combines environments, metadata, tags and relations.

project SaaSPlatform

environment Production {
  element cdn "CDN" as cdn {
    tech "Cloudflare"
    owner "Platform Team"
    monitoring "Cloudflare"
    tags [production]
  }

  element frontend "Customer Portal" as portal {
    tech "React"
    owner "Frontend Team"
    monitoring "Grafana"
    tags [production]
  }

  element gateway "API Gateway" as gateway {
    owner "Platform Team"
    monitoring "Grafana"
    tags [critical, production]
  }

  element service "Tenant API" as tenant_api {
    owner "Backend Team"
    monitoring "Grafana"
    tags [critical, production]
  }

  element database "Tenant Database" as tenant_db {
    owner "Database Team"
    monitoring "Grafana"
    tags [critical, production]
  }
}

relation cdn -> portal : serves
relation portal -> gateway : HTTPS
relation gateway -> tenant_api : REST
relation tenant_api -> tenant_db : PostgreSQL
